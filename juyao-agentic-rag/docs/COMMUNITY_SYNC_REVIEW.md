> 状态：❌ 未完成（方案讨论稿，未实施）

## 背景与问题

社区（Leiden 聚类 + LLM 主题摘要）是 global 检索的数据基础。当前同步机制：

- **触发**：入库完成 → mark_dirty → 30s 静默窗口 → `build_communities(kb, reset=True)`
- **实现**：先删光该 kb 全部社区/MEMBER_OF → 全图 Leiden 重新分区 → 每个社区调 LLM 生成摘要 → 全量写回 Neo4j → Qdrant 摘要全删全写 → MySQL 快照全量重灌

**问题**（按影响排序）：

1. **Token 成本随库规模线性膨胀**：5000 份文档 ≈ 数百社区 → 日常新增 1 份文档也要付一次全库重建的 LLM 费用；社区越多，单次越贵。且 LLM 输出非确定性，未变化的社区每次重建摘要文本都会漂移。
2. **重建期间社区路检索为空**：reset 先删后建，大库重建 20~30 分钟窗口内该 kb 社区摘要检索返回空（问答主路向量+ES+图谱不受影响，社区为增强路，有 best-effort 兜底）。
3. **并发一致性风险**：重建（删+写 Community）与入库（写实体/边）并发，跨连接因果不一致（PITFALLS #8 同源）——批量入库模式下已通过「暂停自动重建」规避，但恢复后仍可能碰撞。

## 现状盘点（2026-08-13 代码实测）

| 环节 | 现状 | 说明 |
|---|---|---|
| 社区检测 | 全图 Leiden（igraph+leidenalg） | 纯图计算，无 LLM，几百实体秒级——**便宜** |
| 社区摘要 | 每社区一次 LLM 调用 | 贵；无缓存、无 diff |
| Neo4j 写入 | 先删光再全量 MERGE | 无版本概念 |
| Qdrant 摘要向量 | reset 删全 collection 再全量 upsert | 与摘要同进退 |
| MySQL 快照 | 四表全删全灌 | 秒级，快照本身便宜 |
| 批量模式 | `set_paused` + `trigger_rebuild_now`（方案 A，已实施） | 批量上传期间只积累 dirty |
| 删除路径 | `_prune_orphan_communities` 清孤儿社区 | 仅删除时生效，与新增无关 |

**结论：全量重建不是增量**——Leiden 部分便宜，LLM 摘要部分是真正的成本大头。

## 方案选型

### 方案 ① 摘要缓存 + 成员 diff（推荐先做）

**思路**：Leiden 照旧全图跑（便宜），跑完后把新分区与旧社区**按成员集合精确对比**——成员集合未变的社区**复用旧摘要**（跳过 LLM + 跳过该社区 embedding）；只有新增/成员变化的社区才重新摘要。

- **省**：日常增量下 80~95% LLM token；未变社区摘要文本稳定（不漂移）
- **成本**：实现小（约半天）——对比逻辑 + 旧摘要读取 + 条件摘要
- **风险**：低。需要对比的对象是「实体 → 社区」归属映射，可以从 Neo4j 读（`MATCH (e:EntityKb{id})-[:MEMBER_OF]->(c:CommunityKb{id})`）
- **细节**：
  - 社区 id 用「成员集合的排序哈希」派生（内容寻址，参考 INGESTION_UPDATE_REVIEW 的 chunk_id 思路）——成员变化 → id 变 → 天然是新社区；id 不变 → 摘要可复用。替代「集合对比」更简单
  - Qdrant 摘要点同样按内容寻址 id upsert，天然幂等去重
  - MySQL 快照照旧全量重灌（便宜），或按新社区 id 差量更新

### 方案 ② 子图增量检测（进阶）

**思路**：只对新文档涉及的实体 + 1~2 跳邻居做局部 Leiden，合并进旧分区，再按 ① 的 diff 处理摘要。

- **省**：再省掉全图 Leiden（本身不贵，边际收益小）
- **成本**：中——局部社区与全局社区的边界质量是难点，需要实验验证
- **风险**：中——边界社区可能分裂/合并失真；Leiden 是全局算法，局部近似理论依据弱

### 方案 ③ 双写切换（解决可用性，不省 token）

**思路**：重建先建新社区（新标签 `CommunityKb{id}.v{n}`），全部完成后原子切换（删旧标签），重建期间旧社区照常可检索。

- **省**：不省 token，只解决「重建期间社区检索为空」
- **成本**：中——标签带版本号，检索侧按版本读；与 ① 正交，可叠加
- **风险**：中——切换窗口的原子性（Neo4j 无跨标签事务切换）

### 方案 ④ 维持现状 + 批量模式（已实施）

大批量场景靠「暂停自动重建 + 手动触发」规避中途浪费（方案 A 已上线）。日常小批量新增场景仍付全量钱。

## 推荐路径

1. **先做 ①**（摘要缓存 + 内容寻址 id）：日常增量 token 省 80~95%，实现小风险低
2. **需要时叠加 ③**：解决重建期间可用性（大库重建 20~30 分钟的窗口问题）
3. ② 视评测结果再说——图计算本身不贵，边际收益不如 ①

## 实施中发现的问题

### P1：CLI Kafka 消费者绕过调度器，仍是一份文档一次全量重建 ❌ 待解决

- **现象**：`python -m rag_core.cli.kafka_consumer` 路径调用 `apply_kafka_ingest_payload(payload)`（默认 `build_communities=True`）→ `ingest_file(..., build_communities=True)` 入库后**立即同步全量重建**；该路径没有任何 mark_dirty，30s 静默窗口策略对它完全失效
- **根因**：两条消费路径行为不一致——Java 监听器 → FastAPI HTTP 路径走调度器（build_communities=False + mark_dirty），CLI 消费者保留历史默认（build_communities=True）
- **当前状态**：线上实际生效的是 Java listener → HTTP 路径（用户 traceback 即 routes/ingest.py），30s 策略正常；但 CLI consumer 一旦有人启动（或与 Java 消费者同 group 分片消费），会回到「一份一建」
- **修复建议**：CLI consumer 改为 `build_communities=False` + 完成后 `scheduler.mark_dirty(kb)` + `scheduler.start()`，与 HTTP 路径对齐

## 待讨论问题

1. 你的使用模式是「日常持续新增」还是「大批量灌库」为主？（决定 ① 的优先级）
2. 社区摘要文本漂移（同一个社区每次摘要都变）是否已造成可感知的检索质量波动？——若没有，① 更多是省钱而非修 bug
3. 重建期间社区检索为空是否有实际影响（问答主路是否已覆盖 90% 场景）？
4. 内容寻址社区 id 会改变现有社区 id 格式（`kb0:community:1` → 哈希），前端展示/聚焦子图逻辑是否需要兼容
